Módulo S7 — BaaS e Tokenização

Novo módulo do Laboratório de Tesouraria de Empresas: quatro cenários interativos sobre Banking as a Service e tokenização, no mesmo padrão pedagógico do módulo S6 (Regulação Bancária) e do cenário-referência “Indústria Alfa”. 1. Visão geral do módulo

O módulo BaaS e Tokenização cobre quatro casos de infraestrutura financeira moderna. Os dois primeiros olham a mesma parceria de BaaS pelos dois lados (o banco licenciado e a marca distribuidora); os dois últimos isolam duas fontes distintas de valor da tokenização (custo de funding e liquidez/risco de liquidação).

2. Premissas, parâmetros e diferenças vs. S6

Este módulo segue o S6 em estrutura, mas com três diferenças explícitas:

  1. Sem chip global. O S6 tinha uma regra única (IB ≥ 10,5%) exibida como faixa fixa. O S7 não tem regra única; cada cenário tem seus próprios parâmetros, que ficam nos KeyFacts. Não implementar o GlobalRuleChip neste módulo.
  2. Caixa ocultável renomeada para “DADOS DETALHADOS” (não “Demonstrações Financeiras”): o conteúdo varia entre unit economics, rotas de funding e fluxos de liquidação.
  3. Sem tabela de FPR. O eixo de cálculo aqui é econômico (margem, take rate, taxa de funding, carry), não regulatório-prudencial.
Parâmetros a marcar como “verificar”: os valores de intercâmbio (sujeito a teto do BCB para débito e a regras por bandeira) e o CDI usado nos cenários são ilustrativos e sensíveis ao tempo. Tratar como premissa de aula; conferir os números vigentes antes de publicar. Os spreads de tokenização e os efeitos de embedded finance são igualmente ilustrativos.

4. Máquina de estados (jornada do cenário)

card → contexto → etapas (3, sequenciais) → encruzilhada → resultado(caminho) → reflexão → conclusão
  1. contexto — narrativa com termos destacados + KeyFacts + caixa ocultável “Dados detalhados”.
  2. etapas — 3 múltiplas escolhas com revelação progressiva: a Etapa N+1 só abre após acerto da N. Cada opção exibe memória de cálculo (verde se certa, vermelha se errada). Erro não pontua e permite nova tentativa. Pontua na 1ª seleção correta.
  3. encruzilhada — 3 cards de decisão (A/B/C); não há “certo”. 0 pontos.
  4. resultado(caminho) — headline + caption + tiles de variação (deltas) + explicação do trade-off.
  5. reflexão — 1 MC sobre o risco residual (25 pts).
  6. conclusão — “PONTUAÇÃO FINAL X / 85” + “Tentar outro cenário” / “Finalizar e voltar”.

Barra de progresso = 3 etapas. Transição 0/85 → 60/85 (fim das etapas) → 85/85 (após reflexão).

6. Modelo de dados (TypeScript)

Mesmos tipos do S6. A única diferença é semântica: statements é renderizado sob o título “Dados detalhados” e não há constante de regra global.

interface KeyFact { label: string; value: string; tone?: "default" | "positive" | "warning"; }

interface DetailTable {            // renderizada dentro do DetailBox ("DADOS DETALHADOS")
  id: string; title: string; columns: string[];
  rows: { label: string; values: string[]; emphasis?: boolean }[];
  note?: string;
}

interface Option { id: string; text: string; correct: boolean; feedback: string; } // feedback = memória de cálculo

interface Etapa { id: string; label: string; prompt: string; options: Option[]; points: number; } // 4 opções, 1 correta, 20 pts

interface DeltaMetric { label: string; value: string; tone: "positive" | "negative" | "neutral" | "risk"; }
interface Resultado { headline: string; caption: string; metrics: DeltaMetric[]; explanation: string; }
interface Branch { id: "A" | "B" | "C"; title: string; summary: string; resultado: Resultado; }
interface Reflexao { prompt: string; options: Option[]; points: number; } // 25

interface Scenario {
  id: string; code: string; order: number;
  title: string; protagonist: string;       // "Banco Trilho S.A." / "VarejoX" ...
  difficulty: "intermediario" | "avancado"; estMinutes: number;
  blurb: string; archetype: string; context: string;
  keyFacts: KeyFact[];
  details: DetailTable[];                     // antes "statements"; título do box = "Dados detalhados"
  etapas: Etapa[];                            // 3
  encruzilhada: { prompt: string; branches: Branch[] };
  reflexao: Reflexao;
  maxScore: number;                           // 85
}

7. Pontuação e persistência

  • 3 etapas × 20 + reflexão 25 = 85. Encruzilhada = decisão (0 pts).
  • Pontua na 1ª seleção correta; erros anteriores não descontam nem readicionam pontos.
  • Estado por cenário: { phase, currentEtapaIndex, answers, chosenBranch, score, completed }; persistir em localStorage por scenarioId.
  • Progresso do módulo (x/4 concluídos) deriva de completed.

9. Convenções de conteúdo

  • Autossuficiência: tudo que resolve as etapas está nos KeyFacts; tabelas volumosas (unit economics, rotas, fluxo) vão na caixa “Dados detalhados”.
  • Memória de cálculo SEMPRE com a conta (fórmula + números). No acerto, reforça o conceito; no erro, aponta o equívoco específico. Cada opção incorreta tem sua memória de erro.
  • Padrão E1 → E2 → E3: E1 = leitura/medida; E2 = mecanismo (o que muda e por quê); E3 = cálculo-síntese que fecha o caso.
  • Cuidado de acrônimo: em tokenização, “RWA” no mercado significa real-world assets; no app, RWA é ativos ponderados pelo risco (módulo S6). Neste módulo, usar sempre “ativos do mundo real / tokenizados” e nunca o acrônimo RWA.
  • Valores em R$; consistentes e implementáveis literalmente.

10. Checklist de QA

  • Os KeyFacts bastam para resolver as etapas? O resto está em “Dados detalhados”?
  • Cada etapa tem 4 opções plausíveis, 1 correta e memória com a conta (inclusive nas erradas)?
  • Os 3 caminhos da encruzilhada divergem (deltas e trade-offs distintos)?
  • A pontuação soma 85 (3×20 + 25)? Transição 0 → 60 → 85 confere?
  • Sem GlobalRuleChip? Caixa ocultável rotulada “DADOS DETALHADOS”?
  • Acrônimo RWA evitado nos cenários de tokenização?
  • Intercâmbio e CDI marcados como premissa “verificar”?
  • Progressão de dificuldade (S7.1/S7.2 intermediário → S7.3/S7.4 avançado)?

S7.1 · Banco Trilho S.A. · Intermediário · 20 min

BaaS: revenue sharing e o break-even do banco licenciado

Blurb (card): O Banco Trilho fornece a infraestrutura bancária (licença, conta, cartão, crédito) para a marca de varejo VarejoX. Como a economia de cada conta se divide entre os dois — e a partir de quantas contas o banco cobre seus custos?

Pergunta-chave: como se divide a economia de uma conta BaaS entre o banco licenciado e a marca, e quanto o banco de fato fica?

Contexto (narrativa)

O Banco Trilho S.A. é um banco licenciado que oferece Banking as a Service: a marca VarejoX embute conta, cartão e crédito no seu app, mas quem detém a licença, o balanço, o capital e o risco de crédito é o Banco Trilho. Em troca, repassa à marca uma fatia da receita (rev-share). Você é da tesouraria do banco e precisa medir a economia por conta, entender por que o split não é simétrico e calcular a escala mínima para o negócio fechar a conta.

Etapa 1 Leitura — receita bruta por conta (20 pts)

Prompt: Qual a receita bruta por conta ativa ao ano?

A) R$ 500 ✓ Correto
Receita bruta = intercâmbio + float + spread + tarifas = 120 + 80 + 270 + 30 = R$ 500.
B) R$ 200 ✗
Erro: R$ 200 é o que vai à marca (40% × 500). A receita bruta por conta é a soma das fontes = 500.
C) R$ 290 ✗
Erro: 290 é a contribuição antes do split (500 − 150 − 60). A receita bruta é a soma das 4 fontes = 500.
D) R$ 470 ✗
Erro: esqueceu as tarifas (30). 120 + 80 + 270 + 30 = 500.

Etapa 2 Mecanismo — por que o split não é 50/50 (20 pts)

Prompt: Por que o rev-share não é simétrico entre banco e marca?

A) O banco detém licença, capital e risco de crédito; a marca detém distribuição/CAC. O split remunera papéis assimétricos. ✓ Correto
O banco aporta balanço, compliance e absorve a PDD (60) e o capital regulatório; a marca aporta a base de clientes. Como os papéis são assimétricos, o split também é.
B) É 50/50 por padrão de mercado. ✗
Erro: não há padrão fixo; o split é negociado e reflete quem carrega risco/capital (banco) vs. distribuição (marca).
C) A marca fica com mais porque assume o risco de crédito. ✗
Erro: invertido — quem carrega o risco de crédito (PDD 60) e o capital é o banco, não a marca.
D) O banco fica com mais porque processa os pagamentos. ✗
Erro: processar é um custo (infra 150), não a razão do split. O que justifica a fatia do banco é licença/capital/risco.

Etapa 3 Síntese — net e break-even (20 pts)

Prompt: Qual o net do banco por conta e o break-even em contas ativas?

A) Net R$ 90/conta; break-even 100.000 contas. ✓ Correto
Net = 60% × 500 − 150 − 60 = 300 − 210 = R$ 90. Break-even = custo fixo / net = 9.000.000 / 90 = 100.000 contas.
B) Net R$ 290; break-even 31.034 contas. ✗
Erro: não descontou o repasse à marca (200). Net = 500 − 200 − 150 − 60 = 90 → break-even 100.000.
C) Net R$ 90; break-even 100 contas. ✗
Erro de escala: 9.000.000 / 90 = 100.000 (não 100).
D) Net R$ 150; break-even 60.000 contas. ✗
Erro: esqueceu a PDD (60). Net = 500 − 200 − 150 − 60 = 90 → break-even 100.000.

Encruzilhada (decisão · 0 pts)

Prompt: Que modelo de contrato adotar com a marca?

Caminho A — Pure rev-share (40% à marca)

Reflexão — risco residual (25 pts)

Prompt: Qual risco residual o modelo de rev-share NÃO resolve para o banco?

A) O banco carrega o risco regulatório e reputacional (KYC/AML, falhas da marca) e fica concentrado num parceiro — se a marca sai, a base evapora. ✓ Correto
O rev-share alinha receita, mas não transfere o risco de compliance/reputação (que é do licenciado) nem dilui a dependência de um único distribuidor.
B) Nenhum: o rev-share alinha tudo. ✗
Erro: alinha receita, não elimina o risco regulatório/reputacional nem a concentração no parceiro.
C) Só falta cobrar mais por transação. ✗
Erro: preço não cobre risco regulatório/reputacional nem a concentração de parceiro.
D) O risco é só o custo de infra subir. ✗
Erro: o risco central é regulatório/reputacional e de concentração, não o custo de infra.

Embedded finance: o ganho da marca ao embarcar finanças

Etapa 1 Leitura — receita atual (20 pts)

Prompt: Qual a receita atual do marketplace?

A) R$ 60 mi ✓ Correto
Receita = GMV × take rate = 500 × 12% = R$ 60 mi.
B) R$ 500 mi ✗
Erro: R$ 500 mi é o GMV (volume transacionado), não a receita. Receita = 500 × 12% = 60.
C) R$ 6,0 mi ✗
Erro: aplicou 12% sobre o GMV incremental (50), não sobre o GMV total (500). Receita base = 60.
D) R$ 12 mi ✗
Erro: o take incide sobre o GMV (500), não sobre a base de clientes. Receita = 60.

Etapa 2 Mecanismo — de onde vem o ganho (20 pts)

Prompt: De onde vem, principalmente, o ganho de embarcar finanças?

A) De três fontes: nova receita financeira; lift do GMV core (conversão/frequência); e retenção/LTV. Não é só “vender um produto financeiro”. ✓ Correto
O efeito principal costuma ser no funil (mais conversão, mais frequência, menos churn) somado às linhas financeiras — não apenas a margem do produto financeiro isolado.
B) Só da nova receita financeira (intercâmbio/float/spread). ✗
Erro: ignora o lift de GMV (6,0), que aqui é a maior parcela.
C) Só do lift de GMV. ✗
Erro: ignora as linhas financeiras (1,0 + 0,5 + 2,5 = 4,0).
D) Apenas de um CAC menor. ✗
Erro: CAC menor ajuda o LTV, mas o ganho medido vem de receita financeira + lift de GMV.

Etapa 3 Síntese — ganho incremental (20 pts)

Prompt: Qual o ganho incremental anual de embarcar finanças?

A) R$ 10,0 mi (+16,7% sobre a receita base) ✓ Correto
Ganho = 1,0 + 0,5 + 2,5 + (10% × 500 × 12% = 6,0) = R$ 10,0 mi. Sobre os R$ 60 mi de base → +16,7%.
B) R$ 4,0 mi ✗
Erro: somou só as linhas financeiras (1,0 + 0,5 + 2,5). Falta o take sobre o GMV incremental (6,0). Total 10,0.
C) R$ 6,0 mi ✗
Erro: contou só o lift de GMV. Faltam as linhas financeiras (4,0). Total 10,0.
D) R$ 16,7 mi ✗
Erro: +16,7% é o ganho relativo; o valor absoluto é R$ 10,0 mi.

Cenário S7.3 — AgroNova Avançado

S7.3 · AgroNova S.A. · Avançado · 24 min

Tokenização de recebíveis: o custo de funding

Blurb (card): A AgroNova precisa antecipar R$ 50 mi de recebíveis de 180 dias. Antecipação bancária, FIDC ou tokenização? Sua tarefa: precificar a rota tokenizada, entender por que a taxa exigida cai e medir a economia.

Pergunta-chave: tokenizar recebíveis reduz o custo de captação frente às rotas tradicionais — e por quê?

Contexto (narrativa)

A AgroNova S.A. tem R$ 50 milhões em recebíveis de prazo médio de 180 dias e precisa de caixa agora. Há três rotas: antecipação bancária (rápida, cara), FIDC (estruturada, regulada, mais lenta) e tokenização (tokens lastreados nos recebíveis, distribuídos a investidores fracionados, com registro on-chain e mercado secundário). Você é da tesouraria e precisa comparar o custo efetivo e decidir a rota.

Etapa 1 Leitura — custo da rota tokenizada (20 pts)

Prompt: Qual o custo da rota tokenizada no ciclo de 180 dias?

A) R$ 3,5 mi ✓ Correto
Custo = 14% × (180/360) × 50 = 0,14 × 0,5 × 50 = R$ 3,5 mi.
B) R$ 7,0 mi ✗
Erro: usou a taxa anual sem ajustar o prazo. O ciclo é 180 dias (×0,5): 14% × 0,5 × 50 = 3,5.
C) R$ 1,5 mi ✗
Erro: usou só o spread (3%). A taxa é CDI + 3% = 14%. Custo = 14% × 0,5 × 50 = 3,5.
D) R$ 4,25 mi ✗
Erro: usou a taxa do FIDC (17%). A tokenização é 14%: 14% × 0,5 × 50 = 3,5.

Etapa 2 Mecanismo — por que a taxa cai (20 pts)

Prompt: Por que a taxa exigida na tokenização é menor que no FIDC?

A) Remove camadas de intermediação, permite fracionamento, o registro on-chain reduz risco operacional/fraude e o secundário aumenta a liquidez → menor prêmio exigido. ✓ Correto
Cedente → plataforma → investidor direto (vs. cedente → FIDC → cotistas): menos camadas e mais demanda fracionada comprimem o prêmio de risco/liquidez.
B) Porque tokens rendem menos por serem digitais. ✗
Erro: a queda vem de desintermediação/liquidez/fracionamento, não de “ser digital”.
C) Porque a tokenização elimina o risco de crédito do recebível. ✗
Erro: o risco de crédito do sacado permanece; o que muda é a estrutura de distribuição.
D) Porque o CDI cai com a tokenização. ✗
Erro: o CDI é exógeno; o que cai é o spread exigido (prêmio sobre o CDI).

Etapa 3 Síntese — economia vs. FIDC (20 pts)

Prompt: Qual a economia de tokenizar em vez de usar FIDC?

A) R$ 0,75 mi por ciclo (≈ R$ 1,5 mi/ano girando 2×) ✓ Correto
Economia = (17% − 14%) × (180/360) × 50 = 3% × 0,5 × 50 = R$ 0,75 mi por ciclo de 180 dias.
B) R$ 1,5 mi por ciclo ✗
Erro: não ajustou o prazo. 3% × 0,5 × 50 = 0,75 no ciclo de 180d (1,5 só anualizado).
C) R$ 4,0 mi por ciclo ✗
Erro: comparou com a antecipação bancária (30%), não com o FIDC. Vs. FIDC = 0,75; vs. banco = 4,0.
D) R$ 0,15 mi por ciclo ✗
Erro: usou diferença de spread errada. A diferença é 3 p.p. (17 − 14): 3% × 0,5 × 50 = 0,75.

Reflexão — risco residual (25 pts)

Prompt: Qual risco residual a tokenização introduz?

A) A liquidez do secundário pode ser ilusória; o vínculo jurídico token↔recebível precisa ser exequível na inadimplência; há risco de custódia/smart contract/plataforma; e a demanda some no estresse. ✓ Correto
A taxa menor pressupõe um mercado secundário líquido e um elo legal robusto entre o token e o lastro — premissas que podem falhar exatamente quando mais importam.
B) Nenhum: on-chain é à prova de risco. ✗
Erro: há risco operacional, jurídico e de liquidez, não eliminados pela tecnologia.
C) Só o risco de o CDI subir. ✗
Erro: o CDI afeta todas as rotas igualmente; o risco específico é jurídico/operacional/liquidez.
D) O token elimina a inadimplência do sacado. ✗
Erro: o risco de crédito do recebível subjacente permanece.

Cenário S7.4 — Tesouraria Mérito Avançado

S7.4 · Tesouraria Mérito · Avançado · 24 min

Liquidação atômica: liberar liquidez e zerar risco de liquidação

Blurb (card): A Tesouraria Mérito liquida R$ 200 mi/dia em T+2. Uma plataforma de razão tokenizada permite liquidação atômica (DvP, T+0). Sua tarefa: medir a liquidez travada, entender por que o atômico elimina o risco de liquidação e quantificar o ganho.

Pergunta-chave: a liquidação atômica (DvP, T+0) libera liquidez e elimina o risco de liquidação — quanto isso vale?

Contexto (narrativa)

A Tesouraria Mérito liquida R$ 200 milhões por dia em operações com janela T+2. Nessa janela, parte da liquidez fica “em trânsito” e existe o risco de liquidação (uma parte entrega e a outra não — risco Herstatt), exigindo um buffer. Uma plataforma de razão tokenizada permite liquidação atômica (DvP, T+0): entrega do ativo e pagamento ocorrem de forma simultânea e condicional. Sua tarefa: medir a liquidez travada, explicar o mecanismo e quantificar o ganho de liberá-la.

DvP = delivery versus payment. Atomicidade: ou ambas as pernas ocorrem, ou nenhuma — não há janela de exposição.

Etapa 1 Leitura — liquidez travada (20 pts)

Prompt: Quanta liquidez fica travada em liquidação no regime T+2?

A) R$ 400 mi ✓ Correto
Liquidez em trânsito = volume diário × dias da janela = 200 × 2 = R$ 400 mi.
B) R$ 200 mi ✗
Erro: contou só 1 dia. Em T+2, dois dias de volume ficam em trânsito: 200 × 2 = 400.
C) R$ 600 mi ✗
Erro: contou 3 dias. T+2 = 2 dias: 200 × 2 = 400.
D) R$ 100 mi ✗
Erro: o volume diário inteiro (200) fica em trânsito por 2 dias: 200 × 2 = 400.

Etapa 2 Mecanismo — por que o atômico elimina o risco (20 pts)

Prompt: Por que a liquidação atômica elimina o risco de liquidação e libera o buffer?

A) Em DvP atômico, entrega e pagamento ocorrem simultaneamente e condicionalmente (ou ambos, ou nenhum) → some a janela de risco Herstatt; T+0 → nada em trânsito → buffer desnecessário. ✓ Correto
A atomicidade remove o intervalo em que uma parte já entregou e a outra ainda não; sem janela, não há buffer a manter.
B) Porque o tokenizado é mais rápido, mas o risco continua. ✗
Erro: a atomicidade elimina o risco de liquidação — não é só velocidade.
C) Porque elimina o risco de crédito da contraparte. ✗
Erro: elimina o risco de liquidação (settlement), não o risco de crédito geral da contraparte.
D) Porque o buffer passa a render mais. ✗
Erro: o ganho é não precisar do buffer (liberá-lo), não fazê-lo render mais.

Etapa 3 Síntese — ganho anual (20 pts)

Prompt: Qual o ganho anual de liberar o buffer com a liquidação atômica?

A) R$ 8 mi/ano ✓ Correto
Ganho = carry negativo evitado = (CDI+2% − CDI) × buffer = 2% × 400 = R$ 8 mi/ano, além de zerar o risco de liquidação.
B) R$ 44 mi/ano ✗
Erro: usou o CDI cheio (11%). O que se evita é o carry negativo (funding − rendimento = 2%): 2% × 400 = 8.
C) R$ 4 mi/ano ✗
Erro: usou metade do buffer. Buffer liberado = 400: 2% × 400 = 8.
D) R$ 8 mil/ano ✗
Erro de escala: 2% × R$ 400 mi = R$ 8 milhões/ano.

Encruzilhada (decisão · 0 pts)

Prompt: Qual caminho de adoção seguir?

Caminho A — Manter T+2 (rails tradicionais)
Custo de mudança zeroMantém buffer R$ 400 miMantém risco de liquidação

Trade-off: nenhum esforço de migração, mas carrega o carry negativo e o risco Herstatt.

Caminho B — Pilotar tokenização numa fatia (25%)
Captura parte do ganhoAprende com risco controladoOpera dois sistemas

Trade-off: ganho parcial e aprendizado, ao custo de integração e dupla operação.

Caminho C — Migrar full para liquidação tokenizada
Captura todo o ganho (R$ 8 mi)Depende de interoperabilidadeFinalidade jurídica e maturidade da infra

Trade-off: ganho integral, mas só funciona se a infra for madura e as contrapartes aderirem.

Reflexão — risco residual (25 pts)

Prompt: Qual condição/risco residual permanece?

A) O ganho só se materializa com efeito de rede (as contrapartes precisam estar na mesma razão); restam riscos de interoperabilidade, finalidade jurídica e dependência da plataforma. ✓ Correto
Liquidação atômica exige que ambas as pernas vivam na mesma infraestrutura; sem adoção das contrapartes, surgem “ilhas de liquidez” e o ganho não aparece.
B) Nenhum: basta o banco adotar. ✗
Erro: precisa que as contrapartes também adotem (efeito de rede).
C) Só o risco de TI interno. ✗
Erro: o risco central é de rede/interoperabilidade/finalidade jurídica.
D) O atômico elimina toda a necessidade de liquidez. ✗
Erro: reduz o buffer de liquidação, não toda a gestão de liquidez da tesouraria.
